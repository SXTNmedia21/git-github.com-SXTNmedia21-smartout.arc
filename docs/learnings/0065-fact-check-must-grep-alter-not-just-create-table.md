# Learning-0065: Fact-Check Must Grep Columns Across ALL Migrations, Not Just CREATE TABLE

## Context

Council 2026-04-19 ran Phase 2.5 fact-check on the WebDayControl implementation plan. The briefing claimed `engine_authority_config` had no `min_role` column. The fact-check agent grepped `CREATE TABLE.*engine_authority_config` and saw only the base columns (`capability`, `level`, `workspace_id`) — confirming the claim.

Result: post-impl R1 kept `hasMinimumRole()` hardcoded in `_shared.ts` with a TODO saying "schema can't support this yet." The spec ADR-0156 §Trust Gate locked this as "acceptable deferral."

A later council (same day, debt-ticket review) caught the mistake: `min_role` column was added by a SEPARATE migration (`20260410000001_add_min_role_to_authority_config.sql`) three weeks earlier. `gate_action()` function already consumes it via `_role_rank()` comparator (`20260509100000_gate_action_four_eyes_history.sql`). The schema work was done; only the caller refactor was missing.

## Discovery

**Single `grep CREATE TABLE.*<table>` is insufficient fact-checking for "does column X exist?"** Columns can be added by:

1. `ALTER TABLE … ADD COLUMN …` migrations dated later than the CREATE TABLE
2. Function/trigger migrations that reference the column (implying it must exist)
3. Seed migrations that INSERT values for the column

The fact-check pattern that would have caught this: `grep -rn '<column_name>' supabase/migrations/` (searches all migration files, not just CREATE TABLE). If the column appears in any ALTER / INSERT / function body, it exists.

## Impact

When fact-checking "does column X exist on table Y":

1. **First pass:** `grep "CREATE TABLE.*Y" supabase/migrations/*.sql` — baseline creation.
2. **Second pass (MANDATORY):** `grep -rn "X" supabase/migrations/` — catches ALTER additions and function references.
3. **Third pass if still uncertain:** Check `packages/supabase/src/database.types.ts` — autogenerated types reflect the final schema state. A column that exists in `database.types.ts` exists in the DB.

The skill of "fact-checking migrations" now has a checklist rule: **never trust a CREATE TABLE grep alone**. A 3-week gap between the briefing's memory snapshot and the actual schema is enough time for ALTER migrations to land.

Applied broadly: any time a council briefing claims "column X doesn't exist" or "feature Y is unsupported by schema," the fact-checker must grep for X/Y identifier across ALL migration files, not just the originating CREATE TABLE.
