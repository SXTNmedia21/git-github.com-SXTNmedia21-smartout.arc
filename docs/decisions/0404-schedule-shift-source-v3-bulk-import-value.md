# ADR-0404: `schedule_shift.source` — Add `v3_bulk_import` Value

## Context and Problem Statement

`schedule_shift` is a D6 Production cascade table. Its `source` column distinguishes provenance
for audit queries, trigger filtering (ADR-0108 Clause B), and selective rollback. The column was
added with a CHECK constraint in migration
`20260515100600_source_discriminator_12_tables.sql:44-46` (the `schedule_shift` block inside the
10-table M7 sweep):

```sql
ALTER TABLE public.schedule_shift
  ADD COLUMN IF NOT EXISTS source text NOT NULL DEFAULT 'operational'
    CHECK (source IN ('operational','bubble_migration','v3_engine'));
```

Current allowed values:
- `operational` — rows written by normal cascade/user operations (default)
- `bubble_migration` — rows migrated from Bubble.io via strike-mcp (ADR-0108 Clause A)
- `v3_engine` — rows generated by the Smartout v3 Event Engine cascade pipeline (ADR-0108
  Clause A)

Sortie C `commit_batch` (per ADR-0401) will write shifts via cascade-delegated helper
`scheduler.create_shift_via_bulk_import(workspace_id, row)` — the `scheduler` capability owning
`schedule_shift` writes (ADR-0173, ADR-0356). These writes MUST be auditably separable from:
- `v3_engine` (ongoing cascade-generated shifts) — a batch-imported vaktliste row must never be
  mistaken for a cascade-generated shift, as rollback, override, and trigger-filter semantics
  differ
- `bubble_migration` (one-time legacy import) — historical Bubble rows are a closed set; new
  bulk imports are workspace-operator-initiated and repeatable

The `v3_*` prefix matches `v3_engine` precedent for Smartout v3-era code paths (as opposed to
`bubble_*` for legacy migration tooling).

**Why the CHECK extends NOW in Sortie A, not Sortie C with the writer:**
Seed data (`supabase/seed.sql`), Sortie B integration tests, and manual smoke runs during Sortie
B+C all need the constraint to accept `v3_bulk_import` before the `commit_batch` writer code
lands. Decoupling the constraint extension from the writer avoids a schema-gate / writer-gate
deadlock: Sortie A cannot green-gate if the constraint rejects values the writer will use, but
the writer cannot be validated without the constraint already accepting the value.

Precedent: `bubble_migration` was added to the same three-value CHECK by the M7 migration
(against a pre-existing two-value state) following the same reasoning — extend the constraint
before writers land, then write writers that stamp the new value.

## Decision Drivers

- Audit + selective rollback require that bulk-imported shifts carry a distinct `source` value
  so `WHERE source = 'v3_bulk_import'` queries are unambiguous.
- Trigger filter migration `20260515100700_engine_process_trigger_filters.sql` uses
  `NEW.source IS DISTINCT FROM 'bubble_migration'` — `v3_bulk_import` rows must fire those
  triggers (same as `v3_engine` and `operational`), so the new value must not be in an exclusion
  allowlist.
- Cascade-delegation pattern (ADR-0356) requires the owning capability's helper to write the
  distinguishing `source` value; that helper ships Sortie C, but the constraint must be in place
  first.
- CHECK widening (adding a value) is always non-breaking for existing rows and existing writers;
  no data migration is required.

## Considered Options

1. **Reuse `v3_engine` for bulk-imported shifts** — Rejected: destroys auditability. A manager
   reviewing `source = 'v3_engine'` rows expects cascade-generated shifts; bulk-imported rows
   mixed in break selective rollback and the "who wrote this?" audit trail.
2. **Use a new column (`import_run_id`) to distinguish bulk-imported shifts** — Rejected:
   `import_run_id` FK already ships in `import_run` row tracking (ADR-0401 schema); adding a
   second discriminator column to `schedule_shift` when `source` already exists as the
   established pattern (10 tables, M7) is unnecessary duplication.
3. **Add `v3_bulk_import` to `schedule_shift.source` CHECK constraint** — Chosen: follows the
   established pattern (ADR-0108 M7), is query-friendly, is trigger-filter compatible, and
   keeps provenance in one column.

## Decision Outcome

**Extend `schedule_shift.source` CHECK constraint to allow `v3_bulk_import`.**

The migration lands inside Sortie A foundation migration
`supabase/migrations/20260624000000_bulk_import_foundation.sql` (Task 4) — the same commit
cluster as the `import_run` table, `fn_fuzzy_match_entity` RPC, and `pg_trgm` extension
registration. The writer helper ships Sortie C.

### Migration SQL (to be applied in 20260624000000_bulk_import_foundation.sql)

```sql
-- ADR-0404: Extend schedule_shift.source CHECK to allow 'v3_bulk_import'.
-- DROP + ADD within a transaction is atomic; existing rows are unaffected (CHECK widens).
ALTER TABLE public.schedule_shift
  DROP CONSTRAINT IF EXISTS schedule_shift_source_check;

ALTER TABLE public.schedule_shift
  ADD CONSTRAINT schedule_shift_source_check
    CHECK (source IN ('operational','bubble_migration','v3_engine','v3_bulk_import'));
```

> Note: PostgreSQL names inline CHECK constraints with the pattern `<table>_<column>_check`.
> The column was added inline in M7 with no explicit constraint name; PostgreSQL auto-generated
> `schedule_shift_source_check`. The `DROP CONSTRAINT IF EXISTS` is idempotent and safe if the
> auto-generated name differs — in that case the ADD still succeeds and the old inline constraint
> is preserved alongside (both will accept `v3_bulk_import` since widening always passes).
> Verify the actual constraint name with:
> `SELECT conname FROM pg_constraint WHERE conrelid='public.schedule_shift'::regclass AND contype='c';`
> before applying to production.

### Writer constraint (Sortie C)

The `v3_bulk_import` value MUST only be written by
`scheduler.create_shift_via_bulk_import(workspace_id, row)` per cascade-delegation (ADR-0356).

```typescript
// In Sortie C: packages/ai/src/capabilities/scheduler/tools/create-shift-via-bulk-import.ts
// (placeholder — writer ships Sortie C, not this ADR)
await supabase.from('schedule_shift').insert({
  ...shiftFields,
  source: 'v3_bulk_import',   // ADR-0404
  // ...
});
```

**Forbidden:** Writing `source='v3_bulk_import'` from any code path NOT in the
`scheduler.create_shift_via_bulk_import` helper. Direct INSERT bypassing the delegation pattern
violates ADR-0173 (frozen-4 capability boundaries) and ADR-0356 (cascade-delegation).

## Consequences

### Positive

- Audit queries `WHERE source = 'v3_bulk_import'` unambiguously isolate bulk-imported shifts —
  rollback, override tracking, and manager review are straightforward.
- Trigger filters in `20260515100700_engine_process_trigger_filters.sql` remain correct without
  modification — `v3_bulk_import` is not in any exclusion list, so bulk-imported shifts fire the
  same triggers as `v3_engine` and `operational` rows.
- The partial index
  `idx_schedule_shift_source ON public.schedule_shift (source) WHERE source <> 'operational'`
  (M7) automatically covers `v3_bulk_import` rows with no index modification required.
- No data migration needed; no existing rows are affected (CHECK widens, never narrows).

### Negative / breaking surface

Consumer code that filters on `source` values may need updating. **Grep audit mandated at Sortie
C close:**

```bash
grep -rn "source.*=.*'operational'\|source IN (" apps/ packages/ services/
```

This catches any allowlist filter that enumerates `source` values and would silently exclude
`v3_bulk_import` rows. All hits must be reviewed and updated if appropriate.

### Reversibility

Reversible by dropping `v3_bulk_import` from the constraint (back to original three values) —
but ONLY if no `v3_bulk_import` rows exist in the table. Once Sortie C lands and
`commit_batch` is exercised in production, reversal is a data-destructive operation and requires
a separate migration with explicit row handling.

## Migration Safety

- `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT` is DDL; PostgreSQL wraps it in an implicit
  transaction. The foundation migration uses `BEGIN … COMMIT`, so the entire Sortie A
  foundation is atomic.
- CHECK widening never rejects existing rows — the migration cannot fail due to existing data.
- `IF NOT EXISTS` / `IF EXISTS` guards make the migration idempotent (safe to replay on a
  reset local database or a rebased Supabase Branch).
- Existing rows: all have `source = 'operational'` (the default) or `bubble_migration` /
  `v3_engine` if pre-populated via seed — all remain valid after the widened CHECK.
