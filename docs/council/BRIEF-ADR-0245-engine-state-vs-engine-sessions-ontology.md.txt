# Council Brief — ADR-0245: engine_state vs engine_sessions Ontology

## Intro — sett deg riktig før du leser videre

**This is the load-bearing ontology decision that unlocks Arena.** Two tables claim the same conceptual ground. Capabilities write `engine_state`; stage-engine reads `engine_sessions`; nothing emits `journey.completed`/`stuck`/`run_failed`. Result: phantom-consumer (B1), Fjernkontroll renders `active` indefinitely, journey-engine campaign shipped writes that no consumer reads.

Until this ADR is accepted, the heartbeat-as-mission-dispatcher pattern (PLAN-arena-harness-migration) cannot pass Phase 2. Every capability migration is gated on this verdict.

**Read in this order:**
1. **§The load-bearing question** — one sentence, the choice we are making.
2. **§Evidence in code** — exact files + line counts so the council does not vote on grep-counts.
3. **§Three options** — what each costs, what each unlocks.
4. **§Recommendation** — Orkestrator's read, with what was weighed.
5. **§Risks of getting it wrong** — symmetric per option.

**Mantra:** *Ontologi er ADR-class. Pluggning er solo.* This is ontology. Council convenes.

---

## The load-bearing question

> **Should `engine_state` be the single canonical runtime table for journey + agent execution, with `engine_sessions` deprecated for journey-flows — or should we maintain a bridge / dual-read pattern indefinitely?**

One sentence, three possible answers (§Three options below).

---

## Why this is ADR-class

Two truths almost-collide:
- **`engine_state`** — written by 4 frozen journey capabilities (ADR-0173) + journey-engine campaign. Schema designed for IR-driven step-by-step execution. Has `engine_state_step` child rows. Status vocabulary: `pending|active|waiting|complete|failed|escalated|blocked` (per M5 R1, commit `36e1d8cc`).
- **`engine_sessions`** — read by stage-engine `core/agent-session.ts`, `guardian-evaluator.ts`, `guardian-bus.ts`, `calendar-guardian.ts`, `stage-manager.ts`, `routes/adapters/telegram.ts`, plus tests. Schema designed for Botsson conversational sessions. Holds session-state for in-flight chats.

Two tables, two histories, partial overlap. Neither was deprecated when the other shipped. The journey-engine campaign handoff (`docs/engines/system-intelligence/11-handoff-capstone.md` §Known Open-Loop) names this explicitly:

> "(a) `services/stage-engine/src/` has zero reads of `engine_state` (reads `engine_sessions` instead). (b) No producer emits `journey.completed`/`stuck`/`run_failed` from capability layer. Fjernkontroll state machine renders `active` indefinitely."

This is the phantom-consumer pattern (related to L-0094, the recurring phantom-emit-contract pattern at 4th recorded occurrence and possibly more after L-0094 was written; tracked further in L-0130 phantom-CONSUMER mirror). It is not a tech-debt cleanup; it is a contract decision per L-0126: *Ontology gap is an ADR, not effort.*

**26 read/write call sites across 9 stage-engine files.** `services/stage-engine/src/core/session-manager.ts` is the largest single file (6 sites, architecturally central — likely non-mechanical rewrite). None read `engine_state` (only `session-recorder.ts` stores an `engine_state_id` reference field).

> **Cost-estimate impact:** earlier draft of this brief understated scope as "14 call sites across 6 files — mostly mechanical." Council should treat the 4-week implementation estimate as a lower bound; session-manager.ts alone may require ~1 week of non-mechanical refactor.

### Capability writes on `engine_state`

`packages/ai/src/capabilities/journey/tools.ts` documents the design at lines 74–91:

> "Insert `engine_state` row (status='pending') + one `engine_state_step` per FLOW step. A separate piece will poll `engine_state` rows with status='pending' [...] then advance engine_state_step rows + emit"

Two insert sites in `tools.ts`:
- **Line 195** — `run_dev` path inserts `engine_state` with `status='pending'`
- **Line 939** — `run_guided` path inserts `engine_state` with `status='active'` per M5 R1 status-vocabulary fix
- **Lines 239 + 991** — paired `engine_state_step` child-row inserts

Capability writes the rows; the "separate piece" (N-C worker) does not exist yet. Stage-engine — the closest thing to a runtime — reads `engine_sessions`, not `engine_state`.

### Telemetry-emit gap

No producer in capability or stage-engine code emits `journey.completed`, `journey.stuck`, or `journey.run_failed`. Registry has the events (5 registered, ADR-0175 — registry uses space convention `journey completed`, dot-notation `journey.completed` is wire format produced by `toDotNotation()` at emit time). The only reference is a docstring in `tools.ts:770` noting that `stuck` is meant to be emitted by the deferred stuck-detector Edge Function (ADR-0215 Option C).

Fjernkontroll state machine at `apps/web/src/components/journey/useFjernkontrollMachine.ts` is a 6-state machine (`idle | running | paused | stuck | completed | failed`). Transition from `running` → `completed` requires receiving a `"complete"` event (line 100). No producer emits the underlying telemetry, so the `"complete"` event never arrives in production. The handoff §Known Open-Loop phrases this as "renders `active` indefinitely" — note that `active` is the DB-status vocabulary; the UI machine state is `running`. Same gap, two vocabularies.

## Three options

### Option A — Consolidate on `engine_state`

`engine_state` becomes the single runtime table for both journey-flows and agent-conversation-sessions. `engine_sessions` deprecated; data migrated; reads in stage-engine rewritten.

**Cost:**
- Stage-engine rewrite: **26 call sites across 9 files** (`session-manager.ts` largest at 6 sites, architecturally central — likely non-mechanical)
- Backfill migration: existing `engine_sessions` rows projected onto `engine_state` schema with `kind='conversation'` discriminator
- Botsson chat migration: stage-engine session-state lives differently
- 7-day parallel-trace per phase to prove zero-divergence
- ~4 weeks build + 1 week soak (lower bound; session-manager refactor may extend)

**Unlocks:**
- Single ontology; FLOW-driven dispatch works end-to-end
- N-C worker has clear target (`engine_state` rows)
- ADR-0215 stuck-detector reactivation possible
- Recurring-mission heartbeat pattern works without bridges
- Phantom-consumer permanently eliminated

**Risk:** Botsson chat session-state is a richer shape than journey-step-state. Requires schema additions on `engine_state` (e.g. `session_kind` discriminator, conversation-specific JSONB columns).

### Option B — Bridge / dual-read

Stage-engine reads union of `engine_sessions` and `engine_state`. Each table keeps its current schema. Application logic dispatches by `mission_id` presence.

**Cost:**
- Add `engine_state` reader paths in 6 stage-engine files
- Application-layer router: "if mission_id present → engine_state, else → engine_sessions"
- ~1 week build, indefinite maintenance

**Unlocks:**
- Journey-flows get a consumer
- Botsson chat unaffected
- N-C worker has its target
- Migration risk minimized

**Risk:**
- Permanent split-brain: two truths, two schemas, two evolutionary paths
- Guardian-bus + guardian-evaluator must mirror logic across both tables
- Future agents must learn both
- Phantom-consumer pattern survives in disguised form
- Eventual cost of consolidation grows with every new capability

### Option C — Consolidate on `engine_sessions`

`engine_sessions` becomes the single runtime table. Capabilities rewritten to write there. `engine_state` deprecated.

**Cost:**
- 4 frozen-by-ADR-0173 capability bodies rewritten (`run_dev`, `run_guided`, `publish_mission`, `publish_guide`)
- `engine_state_step` child-row pattern abandoned or remapped onto `engine_sessions` schema
- Journey IR → `engine_sessions` projection: lossy
- Breaks ADR-0173 contract surface (capability tools have stable input/output)
- ~4 weeks build + heavy review + ADR-0173 amendment

**Unlocks:**
- Stage-engine unchanged
- Botsson chat unchanged

**Risk:**
- ADR-0173 amendment alone is council-class
- Journey IR step-tracking degrades; FLOW-row-per-step pattern doesn't fit `engine_sessions` schema
- Re-introduces phantom-write pattern (capabilities write to a table whose original purpose is conversational sessions, not workflow steps)
- High refactor surface in already-frozen contracts

## Recommendation — Orkestrator's read

**Choose Option A.** Consolidate on `engine_state`.

### Why

1. **Capability layer is contract-frozen (ADR-0173).** Option C breaks four frozen capability bodies + the IR-step-tracking pattern that journey-engine campaign shipped. That is the worst place to absorb the cost.
2. **`engine_state` schema is purpose-built for step-driven execution.** It already has `engine_state_step` child rows, status vocabulary aligned with FLOW-row-per-step, and IR-hash provenance fields. `engine_sessions` was designed for chat-session lifecycles, not step-by-step workflow execution.
3. **Bridge (Option B) creates permanent ontological debt.** Two-truth split-brain compounds with every new agent. We have already paid the discovery cost; we should pay the migration cost once, not in slices forever.
4. **Stage-engine rewrite is bounded but larger than first estimate.** 26 call sites across 9 files (corrected from earlier 14/6 understatement). Most sites are mechanical (`.from("engine_sessions")` → `.from("engine_state")` + status-vocabulary normalization), but `core/session-manager.ts` (6 sites, architecturally central) likely needs non-mechanical refactor. Falsifiable parallel-trace test for 7 days per phase proves correctness before cutover.
5. **Botsson chat absorption is the genuine challenge** — session-state for conversational flows differs from journey-step-state. Solution: discriminator column `engine_state.kind` (`'journey' | 'conversation' | 'recurring'`) plus optional JSONB `engine_state.session_context`. This keeps the table coherent while admitting both shapes.

### What was weighed

- **Option B was tempting** because it is least disruptive in the short term. Rejected because it makes the system structurally weaker over time. Pattern violation: every "additive bridge" we have ever shipped became a tech-debt-magnet within 6 months.
- **Option C was considered** because Botsson is the bigger, older system. Rejected because rewriting frozen-4 capability contracts costs more than rewriting stage-engine reads, and because journey-engine's IR-step tracking is the more sophisticated abstraction (richer ontology absorbs poorer, not vice versa).
- **Option A was chosen** because it pays the migration cost once, in a 4-week bounded window, with a 7-day parallel-trace gate that catches divergence before cutover.

### Implementation outline (post-acceptance)

Phase A1 — Schema unification (1 week)
- Add `engine_state.kind` enum (`journey | conversation | recurring`)
- Add `engine_state.session_context` JSONB nullable
- Migration ships with backfill projection plan, but no data movement yet

Phase A2 — Stage-engine dual-read (1 week)
- Read both `engine_sessions` and `engine_state` where `kind='conversation'`
- Compare; emit `ontology.read_divergence` on mismatch
- Zero behavior change observable to users

Phase A3 — Backfill (1 week)
- Migrate `engine_sessions` rows to `engine_state` with `kind='conversation'`
- Continue dual-read for 7 days; prove zero divergence

Phase A4 — Cutover (1 week)
- Single-read on `engine_state` only
- Mark `engine_sessions` deprecated; reads removed; table preserved for 30 days then dropped in follow-up migration
- Emit `journey.completed/stuck/run_failed` from mission-pool worker (unblocks Fjernkontroll terminal-state)

Total: 4 weeks, gated, reversible at any phase.

## Risks of getting it wrong (symmetric)

| If we accept | Risk |
|---|---|
| **Option A (recommended)** | Botsson chat session-state shape harder to absorb than expected → schema additions become large → mid-migration scope-creep. Mitigated by phase-gates + 7-day parallel-trace. |
| **Option B** | Permanent split-brain → every future agent must learn both tables → dual-codepath bugs (guardian-bus mirrors logic divergently) → full consolidation cost in 18 months grows by every capability added. |
| **Option C** | ADR-0173 amendment + frozen-4 capability rewrite → 4-week scope-creep on capability layer, plus journey IR step-tracking degrades → FLOW-driven dashboard cannot render per-step status. Worst-of-three. |

## What council is asked to vote

**Single question:** A, B, or C?

If A: confirm `engine_state` as canonical, approve Phase A1–A4 outline, authorize ADR-0245 to draft `accepted` with implementation appendix.

If B: name the long-term consolidation horizon (when does B end?). If "never" → name the maintenance cost owner.

If C: authorize ADR-0173 amendment + frozen-4 capability rewrite. Council notes the cost.
