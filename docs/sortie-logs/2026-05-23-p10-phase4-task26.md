## §5 Badge restoration

### Recommendation: (a) — extend PageTabNav with optional `badge` slot

**Rationale:** PageTabNav is already the canonical tab primitive (used here and
elsewhere on the dashboard). Extending it with an optional `badge?: number | string | null` prop
keeps the badge co-located with the tab definition, avoids wrapper DIVs, and means any future
consumer of PageTabNav gets badge support for free. Extension is backward-compatible (prop is optional).
Wrapping externally (option b) would require duplicating tab-position tracking logic in DayControlPanel.
Dropping badges (option c) removes a real affordance managers depend on to see unread state at a glance.

### Sites that need badges restored

CONCERN #6 from the T8 PageTabNav migration dropped four badge data-flows:

| Tab | Badge source | Badge value | Show when |
|-----|-------------|-------------|-----------|
| Dagsinfo (meldinger) | `dayMessages.length` | count | always |
| Reservasjoner (bookings) | `dayBookings.length` | count | always |
| Oppgaver (session-tasks) | `taskCount - taskDone` | outstanding tasks | `taskCount > 0` |
| Økonomi (okonomi) | `settlementStatus` | `"!"` or `1` | status = `submitted` |

All four values are already derived in `DayControlPanel.tsx` (lines 186–197):
`dayStats.messageCount`, `dayStats.bookingCount`, `dayStats.taskCount - dayStats.taskDone`.
`settlementStatus` is queried at line 168. No new data fetching required.

### PageTabNav extension shape (option a)

```ts
// apps/web/src/components/dashboard/PageTabNav.tsx

export type PageTab<K extends string = string> = {
  key: K;
  label: string;
  icon?: ComponentType<SVGProps<SVGSVGElement>>;
  badge?: number | string | null;   // ← add this
};
```

In the tab button render, after `{inner}`:

```tsx
{t.badge != null && t.badge !== 0 && (
  <span
    className="ml-0.5 min-w-[16px] rounded-full bg-accent px-1 py-px text-center text-[8px] leading-tight font-black text-accent-foreground"
    aria-label={`${t.badge} items`}
  >
    {t.badge}
  </span>
)}
```

DayControlPanel would pass badges dynamically by computing `TAB_DEFS` inside the component
(convert from `const` to `useMemo`) and injecting badge values per tab key:

```ts
const tabs = useMemo<ReadonlyArray<PageTab<TabId>>>(() => [
  { key: "oversikt", label: "Oversikt", icon: Info },
  { key: "meldinger", label: "Dagsinfo", icon: MessageSquare,
    badge: dayStats.messageCount || null },
  { key: "bookings", label: "Reservasjoner", icon: CalendarCheck,
    badge: dayStats.bookingCount || null },
  { key: "oppgaver", label: "Oppgaver", icon: ListTodo,
    badge: dayStats.taskCount - dayStats.taskDone > 0
      ? dayStats.taskCount - dayStats.taskDone : null },
  { key: "tidslinje", label: "Tidslinje", icon: Activity },
  { key: "budsjett", label: "Budsjett", icon: DollarSign },
  { key: "bemanning", label: "Bemanning", icon: Users },
  { key: "okonomi", label: "Økonomi", icon: DollarSign,
    badge: settlementStatus === "submitted" ? "!" : null },
], [dayStats, settlementStatus]);
```

**Files affected: 2** — `PageTabNav.tsx` (type + render), `DayControlPanel.tsx` (TAB_DEFS → useMemo).

## Recommended sortie order

1. **T27 — Color tokens first** — largest blast radius (84 hits), but fully mechanical. Ship as one sortie. Zero risk of regressions if token substitutions are verified. Enables T28/T29 to be reviewed on a clean baseline.
2. **T28 — Header chrome** — small, isolated, no data dependencies. After T27 the token vocabulary is confirmed.
3. **T29 — Footer polish + badge restoration** — last because PageTabNav extension touches a shared primitive; audit that no other PageTabNav consumer breaks when `badge` slot added (it's optional so zero breakage expected, but worth a grep).

**Sortie order rationale:** T27 bulk-fixes close the compliance debt; T28+T29 are additive polish that reads better on a color-clean baseline. All three sorties can be done in sequence on the same branch.
