# Journey: Scheduler Web — Proposed Plan Review

## Context

Manager receives a bundle proposal generated by the greedy constraint-solver
(`scheduler.propose_plan` tool via chat or `/api/scheduler/propose-plan` BFF).
The proposal is stored as a single `change_proposal` row with
`kind='scheduler_bundle'` and `status='pending'` per ADR-0309.
The web UI at `/dashboard/schedule/proposed-plan` is the review surface.

---

## Journey: Manager Reviews and Accepts Proposed Plan

**Role:** Workspace manager (manager+ authority level required)
**Entry:** Manager navigates to `/dashboard/schedule/proposed-plan`

**Precondition:**
- At least one `change_proposal` row exists with `kind='scheduler_bundle'` and `status='pending'` for the workspace.
- Manager is authenticated (cookie session).

### Happy path — Accept

1. Browser requests `/dashboard/schedule/proposed-plan`
   → Server Component confirms `auth.getUser()` → user present → renders `<Suspense fallback={<ProposedPlanLoading />}>` shell.
2. `ProposedPlanLoading` skeleton renders immediately (glass card + button placeholders).
3. Client hydrates → `useProposals()` fires `GET /api/scheduler/proposals?status=pending&limit=10`.
4. BFF resolves `workspace_id` + `profile_id` from cookie session (ADR-0151, L-0177 fail-fast if missing).
5. BFF queries `change_proposal` filtered `kind='scheduler_bundle'` + `status='pending'` + `workspace_id` scoped.
6. Response: `{ ok: true, proposals: [{ change_proposal_id, proposed_shift_count, gap_count, objective_score, … }] }`.
7. `ProposalCard` renders:
   - Glass header: date range ("Foreslått plan" + created_at formatted), objective_score badge, N foreslåtte vakter, N udekkede behov.
   - Shift summary ("N vakter klar til opprettelse").
   - Gap warning section (if gap_count > 0).
   - Two buttons: "Godta hele planen" (success) + "Avvis" (destructive outline).
8. Manager reads the summary, clicks **"Godta hele planen"**.
9. Single-sweep gradient animation fires across the glass header card (linear-gradient x-translate from -100% to +200%).
10. `useAcceptBundle.mutate({ change_proposal_id })` → `POST /api/scheduler/accept-bundle` with `{ change_proposal_id }`.
11. BFF re-derives `workspace_id` + `profile_id` (ADR-0151). Calls `acceptProposal.execute()` capability tool.
12. Tool calls `gate_action` RPC → gate approved → transactional apply:
    - `SELECT change_proposal FOR UPDATE` → parse `changes.proposed_shifts[]` JSONB.
    - `INSERT INTO schedule_shift` N rows (all proposed shifts).
    - `UPDATE change_proposal SET status='applied'`.
    - `emit('scheduler.proposal.accepted', …)` ONCE per ADR-0134.
13. BFF returns `{ ok: true, message: "…" }`.
14. Client `onSuccess`: `toast.success("Plan godtatt — vaktene er opprettet.")`.
15. `AnimatePresence` swaps to `AcceptedState` (icon + "Plan godtatt" message).
16. `useQueryClient.invalidateQueries(PROPOSALS_KEY)` → next poll returns empty proposals.

**Postcondition:**
- N `schedule_shift` rows created in DB.
- `change_proposal.status = 'applied'`.
- One `scheduler.proposal.accepted` event in `engine_event` + `activity_trail`.
- UI shows success state.

**Error paths:**
- Auth fails → `useProposals` gets 401 → error state shown ("Kunne ikke laste forslag").
- Proposal already applied → BFF tool returns 409 → `toast.error("Godkjenning feilet: …")`.
- Gate denies → BFF returns 403 → `toast.error(…)`.
- Network error → generic `toast.error` message.

## Journey: Manager Reviews and Rejects Proposed Plan

**Role:** Workspace manager
**Entry:** Manager opens `/dashboard/schedule/proposed-plan`, finds proposal unsatisfactory.

**Precondition:** Same as Accept journey.

### Happy path — Reject

1–7. Same as Accept journey through rendering.
8. Manager clicks **"Avvis"** (destructive outline button).
9. `RejectDialog` opens: title "Avvis plan", description, optional reason textarea.
10. Manager optionally types a reason (e.g., "for mange kveldsvakter").
11. Manager clicks **"Avvis plan"** in dialog.
12. `useRejectBundle.mutate({ change_proposal_id, reason })` → `POST /api/scheduler/reject-bundle`.
13. BFF calls `rejectProposal.execute()` → `UPDATE change_proposal SET status='rejected'` + `emit('scheduler.proposal.rejected', …)`.
14. `toast.success("Plan avvist.")`. Dialog closes.
15. `invalidateQueries` → proposals list empty → `EmptyState` renders.

**Postcondition:**
- `change_proposal.status = 'rejected'`.
- No `schedule_shift` rows created.
- One `scheduler.proposal.rejected` event in telemetry.
- Manager can re-run solver from the schedule view.

**Error paths:**
- Same pattern as Accept — BFF error bubbles to `toast.error`.

---

## Journey: Manager Opens Page with No Pending Proposals

**Precondition:** No `change_proposal` rows with `kind='scheduler_bundle'` + `status='pending'` for workspace.

1. Page loads, `useProposals()` returns `{ proposals: [] }`.
2. `EmptyState` renders: clipboard icon + "Ingen foreslåtte planer" + guidance to run the scheduler.

**Postcondition:** No state change. Manager navigates to schedule view to trigger a new solve.
