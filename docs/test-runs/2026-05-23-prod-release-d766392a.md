### BUG-001 — CORS blocks `activate-workspace` from workspace subdomain (BLOCKER)

**Status:** CRITICAL — blocks workspace bootstrap for new users from `{slug}.smartout.ai`
**Discovered:** T2b (welcome popup → activate-workspace EF)
**Browser error:**
```
Access to fetch at 'https://yljaglomadbhyqpcigff.supabase.co/functions/v1/activate-workspace'
from origin 'https://smartout.smartout.ai' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check:
The 'Access-Control-Allow-Origin' header has a value 'https://smartout.ai' that is not equal to the supplied origin.
```

**Root cause:** 32 Edge Functions import the deprecated static `corsHeaders` constant from `supabase/functions/_shared/cors.ts:66-72` which hardcodes `Access-Control-Allow-Origin: https://smartout.ai`. The dynamic `getCorsHeaders(req)` exists at line 46 and echoes the request origin after suffix-matching `.smartout.ai`, but most EFs haven't migrated (deprecation comment line 62-65 mentions "follow-up PR" not yet done).

**Scope:** 32 files (all `*.ts` importing `corsHeaders`). High-traffic: `activate-workspace`, `bootstrap-cascade`, `workspace-api/*`, `accept-invitation`, `process-notifications`, `push-dispatch`, `send-login-code`, `send-morning-digest`.

**Impact:** Any user on a workspace subdomain hits CORS on most data + write endpoints. Bootstrap-flow is the first observable symptom because it's the first thing a new user does. ALL existing workspace-subdomain users likely affected too on any EF call.

**Fix path:** Migrate all 32 files: `import { corsHeaders }` → `import { getCorsHeaders }`, replace `corsHeaders` references with `getCorsHeaders(req)` at handler level. Mechanical change. Hotfix to main → CI deploys all EFs.

**ADR ref:** ADR-0171 (follow-up PR mentioned in cors.ts:13 — never landed).

**Fix-in-flight:** Sub-agent dispatched (agentId redacted). Branch `hotfix/cors-subdomain-migration` from main. Migrates all 32 files + deletes deprecated export + adds CI gate `check:cors` + ADR-0408. PR pending.

### BUG-002 — Resend invitation fails with unique-index collision (HIGH)

**Status:** HIGH — blocks invitation resend for phone invites after 1st resend
**Discovered:** T_invite-resend
**Error (server action `resendInvitation`):**
```
Failed to create invitation: duplicate key value violates unique constraint "idx_invitation_unique_phone"
```

**Root cause:** Index `idx_invitation_unique_phone` on `(workspace_id, phone, status)` (partial `WHERE phone IS NOT NULL`) created 2026-03-01 (`supabase/migrations/20260301220023_invitation_sms_support.sql:34-36`).

Resend flow:
1. `UPDATE invitation SET status='cancelled'` on the original pending row
2. `INSERT` a new row with `status='pending'`

After 2+ resends, multiple rows accumulate with `status='cancelled'` for the same `(workspace, phone)`. The partial unique index treats them as duplicates (status is part of the key tuple but cancelled-cancelled collides with cancelled-cancelled).

Email got the correct fix 2026-05-15 (`workspace_invitation_pending_unique_per_email` — partial unique `WHERE status='pending'`, per ADR-0169). Phone was never mirrored.

**Affected paths:**
- `apps/web/src/app/dashboard/people/_actions/people-actions.ts:395` (`resendInvitation`)
- Any phone-channel SMS resend flow

**Fix:**
1. DROP `idx_invitation_unique_phone` (status-in-key behavior)
2. CREATE `workspace_invitation_pending_unique_per_phone` partial unique `WHERE status='pending' AND phone IS NOT NULL`
3. Cleanup migration: dedupe existing cancelled rows (keep newest per workspace+phone+status)

ADR ref: ADR-0169 (email precedent — phone should mirror).

### BUG-005 — Invite-accept never creates profile in target workspace (CRITICAL)

**Status:** CRITICAL — invitation system broken end-to-end. Invited users cannot join.
**Discovered:** After completing the accept → reset-password → login sequence (BUG-003 workaround), user lands on:

> "Velkommen til Smartout
> Du er ikke medlem av noen arbeidsflater ennå.
> Ingen arbeidsflater ennå. Be en admin om å invitere deg — eller opprett din egen.
> [Opprett arbeidsflate] [Logg ut]"

**Expected:**
- Accept link consumes the invitation token
- Server creates a `profile` row binding `user_identity ↔ workspace` with role from invite
- User lands on the workspace dashboard, not "no workspaces" screen

**Hypothesis (verify):**
- `accept-invitation` EF expects an authenticated session WITH the invitation token in the same request — but the redirect-to-login flow loses the token (returnTo URL doesn't preserve `?token=...`)
- OR the EF runs but auth user was created BEFORE token verify and the FK-link step was never reached
- OR the EF runs and creates the profile, but for the WRONG workspace (defaults to none)

**Chain of failure (cascading):**
1. BUG-003 — accept link → login (no instructions)
2. User uses "forgot password" → reset → login
3. Login succeeds → `user_identity` row exists in auth.users
4. Invitation token NEVER consumed during step 2-3 (lost in redirect)
5. `profile` row never created
6. User lands on "no workspace" empty state (BUG-005)

**Critical path:** invitation system is the ONLY way prod users come on board. This blocks ALL onboarding. The bootstrap CORS issue (BUG-001) only blocks workspace-creator first-login; invitation-acceptance failure blocks every employee/manager onboarding after that.

**Need to verify:**
1. Does `auth.users` have the new user? (yes if reset-password worked)
2. Does `invitation` row still have `status='pending'`? (then token wasn't consumed)
3. Does `profile` have any row for that user? (probably no rows = bug confirmed)

**SQL (run against prod):**
```sql
-- 1. Did invitation get consumed?
select invitation_id, email, status, accepted_at, accepted_by, workspace_id
from public.invitation
where email = '<accepted-email>'
order by created_at desc
limit 5;

-- 2. Did profile get created?
select p.profile_id, p.user_id, p.workspace_id, p.role, p.status, p.created_at
from public.profile p
join auth.users u on u.id = p.user_id
where u.email = '<accepted-email>';

-- 3. Did auth user get created (sanity)?
select id, email, created_at, last_sign_in_at
from auth.users
where email = '<accepted-email>';
```

If invitation.status still 'pending' AND no profile row → token never reached server. Fix at the redirect-loss point.

- Invitation `332688fb-…` for that email is still `status='pending'` with `opened_at=18:56:25` (link was clicked)
- Token NEVER consumed despite successful signin

**Code path of failure:**

**Status:** CRITICAL — blocks contract-send + any other service-to-service flow (voice-agent, shift-mcp, stage-engine likely affected too)

- shift-mcp — likely broken (verify)
- stage-engine — uses different auth path, but worth checking
- Any external partner using a workspace API key — also broken

- Inserted via MCP into `platform_api_key` (id `4bb82730-6cbb-4ff7-add7-69881c1f254b`)

**Structural fix needed (own sortie):**
