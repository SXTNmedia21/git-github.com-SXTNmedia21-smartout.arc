# ADR-0001: Phase 3.5b Auto-Align Workflow

## Status

Accepted. Council convened 2026-04-08 with 3 reviewers (Plan, code-architect, independent auditor). User approved verdict with defaults (Q1=A, mandatory-only refinements, no reference scan).

## Context

Phase 3.5a Discovery succeeded — 20 real mappings, 229 v3 tables parsed. Phase 3.5b must align Bubble fields to v3 columns. The choice was: (a) human reviews every field via `review_mapping.ts` (tedious, O(hours)) or (b) auto-align with strict rules + focused human input on strategic decisions.

Council verdict: **(b) with mandatory refinements**. Human review is needed but at strategic/batch level, not per-field.

## Decision

### Core workflow

1. **Round 1 (autonomous, ~3 hours):** `scripts/auto_align.ts` reads all 20 mappings + `v3_schema.json`, applies strict alignment with type-compatibility gate, writes shadow output + per-entity markdown reports.

2. **Round 2 (user, ~30 min):** User reviews reports and makes 6-8 batch strategic decisions. No per-field work.

3. **Round 3 (autonomous, ~10 min):** Apply decisions, compute approval hashes, promote shadow to committed mappings.

4. **Phase 3.5c:** Validation with approval-hash gate.

### Q1: auth.users strategy — Option A (locked)

- Skip `auth.users` migration entirely
- Migrate `profile` → v3 `public.profile` directly
- Migrate `🎎invitation` → v3 `public.invitation` directly
- Use deterministic UUIDv5 from Bubble email so post-cutover invitation flow matches identity correctly
- Rationale: v3's `handle_new_user` trigger owns `auth.users`; bypassing it fabricates auth state. Bubble already has 39 invitation records — 1:1 match.

### Mandatory refinements (blocking implementation)

**Governance (4):**
1. Hard-ban sidecar access — test mocks fs, fails on any path under `mappings/.local/`
2. Shadow directory writes — `mappings/.aligned/` on first pass, explicit `--commit` to promote
3. Preflight invariants — abort if git-dirty, prior marker exists, or schema hash mismatch
4. Approval hash — SHA-256 of canonical-JSON embedded as `approval_hash` field; Phase 3.5c refuses mismatched files

**Correctness gates (4):**
5. Type-compatibility matrix (13 rules, see full list in council report) — `string<32>` → uuid forced review, etc.
6. Date gate requires name + length (not length alone) — avoids auth_token false positive
7. NOT NULL v3 columns without defaults → hard block entity (not warn)
8. Timestamp column transforms — explicit mode: `preserve` / `regenerate` / `copy`

**Report quality (3):**
9. One markdown file per entity + `auto_align_SUMMARY.md` dashboard
10. Four sections per entity report: summary / confirmed (collapsible) / DROPPED (with fill-rate buckets) / review queue
11. Fill-rate bucketing on drops: `always 100%`, `mostly >50%`, `sparse <50%`, `empty 0%`

**Operational (1):**
12. Determinism test — double-run produces byte-identical output

### Entity-specific notes

- `workspace` (43 fields) — expect heavy drop. Highest review priority.
- `shifts` (25,333 records) — strictest type-compatibility. No auto-confirm on any FK column.
- `users` — expected 100% drop given Q1=A. `profile` + `invitation` carry the identity data.
- `salary_rules`, `time_rules`, `rule_templates` (0 records) — auto-attest `known_empty_source: true`, keep `needs_review: true`.
- `subtasks` — auto-detect fold-candidate (if v3 `task.parent_id` exists, surface option).

### Should-haves (add if time permits)

- Source-side collision detection (two Bubble fields normalize to same v3 column)
- S5 field overlap matrix for rule variants
- Tri-state `target_table`: `null | string | "__dropped__"`
- `mapping_schema_version: 1` structural marker

### Deferred

- Reference scan (grep n8n/mobile exports) — user declined
- `.error.json` awareness — 7 entities have them but not blocking

## Consequences

- Phase 3.5b becomes ~4 hours wall time (3 build + 1 review + 10 apply)
- Phase 4-6 plans (deprecated) can be deleted after 3.5c validates
- Auto_align script becomes a permanent tool for future customer migrations — runs per workspace
- PII posture: hard-ban enforced mechanically, not by convention
